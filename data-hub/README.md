# Venezia MeteoMarine Data Hub — phase 1

Independent Node 22+ process: `node data-hub/server.js`. No dependencies beyond existing repository. Default: zero external requests. Configure HUB_STATE_DIR on a durable writable volume (one instance only), HUB_CONTACT_URL public contact page, HUB_READ_TOKEN optional read-only server secret, and HUB_ENABLED_FEEDS only for sources whose automated access and redistribution have been confirmed. Do not enable a denied source on a different host to evade its decision. HTTP 403 persists in state; operator review and explicit publisher authorization are required before resetting that group. HTTP 429/503 respect Retry-After. The BETA page and official table require separate confirmation of conditions; not enabled automatically. Never use prohibited paths or graphical extraction. Polls every five minutes per feed with ten-second group spacing, status cached on disk; HTTP clients never initiate upstream requests. This initial version needs persistent storage; Render Free disk and Vercel functions alone are not suitable for this process. No production service is created. Storage failure is fatal to the poll, not a reason to reset cooldowns.

Read-only endpoints: /healthz, /api/v1/status, /api/v1/feeds/{livello,previsione,vento,pressione,tempacqua,umidita,temparia,cpsm-web,cpsm-table,ispra-level,metar}. Raw validated snapshots preserve the existing PWA parsers and charts; clients must continue per-station freshness checks. Source provenance stays native. No arbitrary URL proxy. Once enabled and tested, configure METEO_HUB_URL=https://<approved-hub-host> and optional METEO_HUB_TOKEN in both PWA servers; no direct retry of mapped sources if hub is unavailable. Existing independent backup logic and local archives remain. vePORTO and MOSE are now mapped; vePORTO uses HUB_VEPORTO_USERNAME and optional HUB_VEPORTO_PASSWORD only in hub memory, after authorization. CSV archive remains separate. History SQLite uses WAL and stores original per-station timestamps, deduplicated; 30 days tide, 48 hours meteo/visibility, 7 days forecast/MOSE. GET /api/v1/history/<feed>?from=<epoch-ms>&to=<epoch-ms>&limit=200&station=<cursor-station> returns bounded pages; next cursor uses from and station. Raw snapshots are not an unrestricted proxy. MOSE confirmation time is independent of official state-change time. Durable volume is required; SQLite and state-v1.json must be backed up together using SQLite online backup, not live file copies. Production archive migration and UI history import remain follow-on work. No secrets committed. 

Test: node --test data-hub/test.js; existing tide/meteo regression tests. No real requests in tests. Production cutover only after approved source access, verified timestamps, full UI tests and disabling duplicate collectors. Existing main remains unchanged.

Production read token mandatory (minimum 32 characters). APIs do not expose credentials or act as a general network proxy. MOSE confirmation age is maintained on upstream 304 only; hub reads never renew it. Unit tests cover deduplication, disk restart, disabled sources, 403 lock, vePORTO credential isolation, and expired MOSE snapshots.

## Standalone deployment
Copy only the contents of `data-hub/` to a new initialized repository (not the whole TPL history). `npm test` and `npm start` run without external dependencies using Node 22.13+; set variables at the hosting provider, not in Git. For now, backup/restore procedure: stop the single hub process, copy the complete state directory (including SQLite sidecar files if present) to protected persistent storage, restart; test restore in isolation with all feeds disabled. A production scheduler and storage hosting choice are still required. A global 600-request/minute cap and read-token auth are implemented; edge limits and TLS are still required. The `/about` endpoint is public and the read-only health endpoint does not expose credentials.

## Optional Playwright transport (0.3.0)
Only the public MOSE status page can use this transport, after the provider confirms automated access. Set `HUB_MOSE_BROWSER=true` together with explicitly enabled `mose`. Default false. CPSM and vePORTO retain the existing approved HTTP path; Chromium is not a retry or alternative route after denial. No fingerprint alteration, stealth plugin, challenge solving, proxy or cookie import. Chromium uses sandboxing, fresh isolated context, declared hub User-Agent, HTTPS validation, GET-only same-origin resource rules, blocked WebSockets and service workers, fixed destination and bounded table extraction. Hosting must independently restrict network egress (browser request routing alone is not a complete security boundary). Any explicit denial is persisted by the hub; 429/503 respect cooldown. No fallback to another transport. Browser memory is released after each acquisition. Install optional pinned Playwright dependency, then run `npx playwright install --with-deps chromium` in the standalone package on a compatible Linux host; do not disable sandboxing. CI includes a real Chromium smoke test with an offline fixture, not a request to an upstream source. Lockfile generation and production resource/egress validation remain required before release.

## Current runtime (v0.4.0; supersedes earlier transport notes)
Production acquisition has exactly one transport: Playwright Chromium headless. No global fetch fallback in the hub core or server. Eligible sources are MOSE, ISPRA level and METAR, each individually enabled only after automated access is confirmed. CPSM and vePORTO remain suspended at the production engine boundary; their registry, existing parsers and test fixtures are retained for future authorized integration once access restrictions are resolved. No alternative host or browser retry for a denied publisher. Tests use dependency-injected fixtures, not production network. The browser has sandboxing enabled and never processes challenge pages. JSON/XML navigation has scripts disabled and fixed endpoint restrictions. The application still distributes stored data over its own read-only HTTP API. The existing PWA clients and main branches remain untouched. CI uses Ubuntu 22.04 to test sandboxed Chromium; no --no-sandbox fallback. Production requires ingress TLS, network egress controls, durable disk and a tested browser-compatible host. The body size check in browser responses happens after Playwright receives the body; hosting must also impose memory/network limits.
